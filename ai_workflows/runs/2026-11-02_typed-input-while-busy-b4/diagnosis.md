# Diagnosis — typed input while JARVIS is listening (phase B4, N-PC2)

Read-only, on `2d35a0a`. The reproduction script is `evidence/probe_before.mts` and its output is `evidence/probe_before.txt`. It uses a throwaway data folder and a fake TTS, and calls no model.

| # | Finding | Evidence |
|---|---|---|
| D1 | `orchestrator.process()` checks two things before running a request. If JARVIS is SPEAKING or INTERRUPTED, it treats the input as a barge-in and moves to PROCESSING_STT. If a request loop is still running (`_loopExecuting`), it aborts that loop and resets to IDLE. Any other state is left unchanged. | `core/orchestrator.ts:303-329` |
| D2 | The agent loop then moves straight to PLANNING, both for the fast routes and for the planner. The state rules allow PLANNING only from IDLE, PROCESSING_STT and REPAIRING. So from LISTENING (after the wake word, while speech is recorded) and from REFLECTING the transition throws. The error reaches the loop's catch, which says "I encountered an unexpected error, sir. Please try again." | `core/agentStateMachine.ts:84-93`; `core/orchestrator.ts:864` |
| D3 | Reproduced. Typing "open notepad and tell me a joke about cats" in LISTENING, and again in REFLECTING with no request running, gave `ILLEGAL TRANSITION REJECTED: LISTENING -> PLANNING` (and `REFLECTING -> PLANNING`). Both times JARVIS said "I encountered an unexpected error, sir. Please try again." The request was not run. | `evidence/probe_before.txt` |
| D4 | Speech normally goes from LISTENING to PROCESSING_STT first, in `jarvis.ts`; when JARVIS is busy it is queued ("One moment, sir"). Two voice paths also call `process()` directly: the queue drain, which moves to PROCESSING_STT first, and the "arbitrated" fast route while busy, which runs only in PLANNING to REPAIRING. So only CLI text can reach `process()` in LISTENING, but arbitrated voice can reach it in a left-over state. *(Corrected after review R7.)* | `jarvis.ts:231-233, 683-698, 905-909` |
| D6 | One likely source of a left-over state: a request that was superseded clears `_loopExecuting` in its `finally` without checking it is still the current call, so the flag can read false while the newer request runs (review R2, probe P2). For typed text the new reset branch then fires (typed text only, since review N1), and the log line now says "no request marked running". The newer request's controller was already aborted by then, so the reset does what the concurrent branch would do. Fixing the flag itself is a follow-up. | `core/orchestrator.ts:459`; review probe P2 |
| D5 | On the owner's PC, LISTENING followed the wake word ("Jarvis"), which the open microphone picked up while the owner was typing (2026-11-02, 20:56:45). | owner's log |
